1. Objective

Build a small REST API for managing Projects and their associated Tasks using a relational database.

The API should provide a clean and maintainable implementation with proper validation, error handling, HTTP status codes, and database relationships.

2. Domain Model

The system contains two main entities:

Project

A Project represents a collection of related tasks.

Attributes:

id
name
createdAt
Task

A Task represents a unit of work that belongs to a Project.

Attributes:

id
projectId
title
completed
createdAt


3. Entity Relationship

A Project can have multiple Tasks, while each Task belongs to one Project.

Project (1) ─────────── (*) Task (projectId → Project.id)


The relationship will be enforced using a foreign key constraint in the relational database.


4. Functional Requirements
Projects

must support:

Retrieving all projects.
Creating a new project.
Retrieving a specific project together with all his tasks.
Tasks

must support:

Creating a task for a specific project.
Updating an existing task.
Deleting an existing task.

5. API Endpoints

Projects
GET	/projects	#Return all projects
POST	/projects	#Create a new project
GET	/projects/{id}	#Return a project with all its tasks

Tasks
POST	/projects/{id}/tasks	#Create a task for a project
PUT	/tasks/{id}	             #Update a task
DELETE	/tasks/{id}	          #Delete a task


6. Validation Requirements

The API must validate all required input fields.

At minimum:
Project name must be provided.
Task title must be provided.
A task cannot be created for a project that does not exist.


7. Error Handling

The API must return meaningful errors when requested resources cannot be found.

Examples:

Requesting a non-existent project → 404 Not Found
Creating a task for a non-existent project → 404 Not Found
Updating a non-existent task → 404 Not Found
Deleting a non-existent task → 404 Not Found
Invalid request data → 400 Bad Request

8. HTTP Status Codes

The API will use appropriate HTTP status codes according to the operation.

Expected responses include:

200 OK — Successful retrieval or update.
201 Created — Resource successfully created.
204 No Content — Resource successfully deleted.
400 Bad Request — Invalid request data.
404 Not Found — Requested resource does not exist.

9. Database Requirements

The system must use a relational database.

The database must contain:

A Projects table.
A Tasks table.
A foreign key from Tasks.projectId to Projects.id.

Database schema creation will be provided through EF Core migrations.

10. Code Quality Requirements

The implementation should:

Follow a clean and maintainable project structure.
Separate responsibilities between application layers.
Use DTOs for API contracts.
Keep controllers focused on HTTP concerns.
Keep business logic outside controllers.
Validate request inputs outside controllers through the application pipeline.
Keep business-rule validation within the business layer.
Provide meaningful naming and readable code.
Include unit tests for important business behaviors.

11. Assumptions
Project and Task identifiers will be generated using GUIDs rather than sequential numeric identifiers.
GUIDs are used to provide globally unique identifiers without relying on a centralized sequence or database-generated numeric values, which makes the identifiers suitable for distributed systems and future scalability.
createdAt is generated by the server.
A Task belongs to exactly one Project.
